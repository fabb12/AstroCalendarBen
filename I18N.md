# Internationalisation

The application exposes one internationalisation service as `window.astroI18n`.
Legacy screens are translated from their original Italian DOM text for
backwards compatibility. New interface code must not add text literals to
HTML or JavaScript: it must use message keys.

## New dynamic text

```js
status.textContent = astroI18n.t('weather.loading');
```

Messages may contain named placeholders:

```js
astroI18n.t('results.count', { count: results.length });
```

Missing keys are intentionally shown as the key itself and reported in the
console, rather than silently leaking copy from another language.

## New static text

Use `data-i18n` on text-only elements. Keyed variants are available for the
three accessibility and form attributes used by the application.

```html
<button data-i18n="actions.save"
        data-i18n-title="actions.saveHelp"
        data-i18n-aria-label="actions.save"></button>
<input data-i18n-placeholder="search.placeholder">
```

## Adding a language

Register its metadata and complete message catalogue before initialisation:

```js
astroI18n.registerLocale('fr', {
  locale: 'fr-FR',
  manifest: 'manifest-fr.json',
  messages: {
    'language.switch': 'Passer en {language}',
    'app.title': 'AstroCalendrier de Ben'
  },
  exact: new Map(),
  fragments: [],
  glossaryEntries: [],
  glossary: new Map()
});
```

The language selector reads the registry, so no menu or switching code needs
to change when another locale is added. `getSupportedLanguages()` returns the
registered codes and `getLocale()` returns the locale used by `Intl`.

During the legacy migration, `exact`, `fragments`, and `glossaryEntries` can
translate old DOM copy. They should not be used by new features: keyed
messages are deterministic, auditable, and do not depend on sentence order.
